# Architecture

## Why no build step

The site is static HTML, CSS and native ES modules. GSAP is vendored, and fonts are self-hosted.

- **Hosting.** It deploys as-is to GitHub Pages or any static host, which is how INVITÉ already ships client work.
- **Longevity.** There is no toolchain to update before a one-line text change.
- **Speed.** Each page loads only what it needs. The homepage modules are loaded with `import()` and start independently.
- **Privacy.** No CDN or font-service requests, which matters for EU and German visitors.

When to move to a build (Vite is the natural next step): if the site gains many pages, a CMS, or a Georgian edition that needs shared templates. The modules already use relative ES imports, so Vite can bundle them without rewrites. The header and footer would then become partials instead of repeated markup.

## Opening pages from disk

Browsers block ES modules and web fonts on `file://` pages. So that double-clicking `index.html` still shows the full site, an inline script in each page detects `file:` and loads `js/offline.js` and `css/fonts-offline.css` instead. Both are generated by `tools/build-offline.py`:

- `js/offline.js` combines the 30 modules into one classic script with a tiny module registry. Imports become lookups, `import()` becomes a promise, and folder links such as `work/jetour/` are pointed at `index.html`, because a folder opened from disk shows a file listing.
- `css/fonts-offline.css` embeds the four fonts as data URIs.

`main.js` starts the site only once (`window.__inviteStarted`), so a browser that loads both copies still starts it once. Rerun the script after editing `js/` or the fonts.

## Pages

| Page | Loads |
|---|---|
| `/` | All CSS, GSAP (deferred; `vendor/gsap.min.js` only, no plugin is loaded), `js/main.js`, which imports intro, hero, work, solutions, method, contact and footer |
| `/work/*/` | Shared CSS plus `case.css`, then `main.js` → `work/CaseStudy.js` and the footer. No GSAP. |
| `/privacy/`, `/legal/` | Shared CSS plus `legal.css`, then `main.js` → navigation and footer only |
| `/404.html` | Self-contained: inline CSS, no scripts |

`js/main.js` wraps every module in `safe()`, so one failing module never takes the page down.

## Graphics

**Quality presets** (`js/core/quality.js`) are decided once per page from a WebGL probe that tells a real GPU from software rendering, plus device memory, CPU cores, data saver and screen size:

- `high`: full resolution, device pixel ratio up to 1.75
- `medium`: reduced resolution and geometry, pixel ratio up to 1.25
- `low`: static fallbacks (no GPU, data saver, very low memory).

Override with `?quality=low|medium|high`.

**GPU scheduler** (`js/core/gpu.js`). Only one WebGL workload runs at a time. The intro takes exclusive focus and pauses everything else. (The homepage has no other WebGL scene: Fig. 01 is SVG and runs its small animation only while on screen.)

**Lifecycles.** Every WebGL scene handles:

- resize, through a ResizeObserver with the DPR cap
- context loss and restore
- full disposal: buffers, textures, programs, then `WEBGL_lose_context`
- pausing when hidden

The intro draws its first frame before its timeline starts, so shader compilation never eats into the sequence. It releases its context only when the browser is idle after the hand-over.

**Intro decision.** An inline script in `<head>` chooses the mode before first paint, so there is no flash:

- `full` on a first visit (about 2.8 s)
- `short` for returning visitors and on reload (about 1.2 s)
- `classic` only with `?intro=classic`: the earlier 5.7 s sequence, kept so the two can be compared
- `none` for a link to a section such as `#contact`, the way back from another page of the site (same-origin referrer or the browser's Back button), or `?intro=off`

How it plays depends on the device: the television runs wherever WebGL exists (at half resolution on the `low` preset; a CRT forgives it), a static frame plays without WebGL, and with reduced motion a still frame simply fades.

An inline fallback opens the `<dialog>` immediately and releases it after 6 s if the module never loads. Skip and Escape work from the first frame. Once the module owns the intro it has its own limits (`START_LIMIT`, `RUN_MARGIN`, `HARD_LIMIT` at the top of `IntroExperience.js`): the television may take 6 s to start, a running sequence may overrun its length by 3 s, and a skip releases the page within 1.5 s whatever the animation is doing.

## Creative Solutions

The section presents four services (001 Get noticed, 002 Build anticipation, 003 Make an impression, 004 You’re invited) as a compact mosaic: a twelve-column grid ruled by 1px gaps, 001 across the full width, then 002 and 003 at 7/5, then 004 across the full width with its title and text swapped, so the eye does not read the same shape twice. Content lives in `js/solutions/solutions.js`; `tools/render-solutions.mjs` writes each tile followed by its details between the `solutions:mosaic` markers in `index.html`, so all copy is in the HTML. The same command writes the four service links under the hero (`solutions:strip`) and the compact invitations block of Selected Work (`solutions:invites`, from the live projects of 004 in `projects.js`; `renderInvites` in `js/solutions/catalog.js`), so no project name, address or picture is typed twice. The grid uses `grid-auto-flow: dense`, so a detail panel (full width) drops below its row while the neighbouring tile stays beside the open one. The service ids are stable (`get-noticed`, `build-anticipation`, `make-an-impression`); the retired ids are redirected in `CreativeSolutions.js` (`LEGACY_IDS`).

### Project catalog

Each Details panel ends with a "See Project Catalog →" row and a drawer that opens in place under the details.

```
projects.js ──┐
solutions.js ─┼─► tools/render-solutions.mjs ─► index.html   (build time; validates, then writes)
catalog.js ───┘                                  └─ per service: the toggle row + the catalog drawer
render.js ─► renderDetail(service, catalogMarkup)   (the drawer is appended at the foot of the panel)
```

- **One data source.** `projects.js` holds every project once, with a `services` array, so a project appears in several catalogs without duplication. `projectsFor(serviceId)` returns the showable projects for a service in list order; a project without a cover image, alt text or a known status is skipped.
- **Build-time only.** `projects.js` and `catalog.js` are imported by the Node tool only. They are not in the page's module graph, so visitors do not download project data and `tools/build-offline.py` does not bundle them. (`CatalogSpreads.js` is in the module graph, but it only reads the markup and holds no project data.)
- **Validation before writing.** The tool refuses (and leaves `index.html` untouched) when a cover, `srcset` or screen file is missing, a screen has no `alt` or a malformed `size`, `previewTone` is not a hex colour, `catalogLayout` is not `cards` or `spread`, `caseStudyUrl` is absolute or its page does not exist, `liveUrl` is not `https://`, a service id is unknown, or an id is duplicated. Warnings: skipped projects, a `liveUrl` on a non-live project, more than three screens (only three are shown), a project with no screens in a catalog set as spreads (its cover is shown alone).
- **Honest cards.** The "View Case Study" button needs a valid internal route; "Explore Live Experience ↗" needs a live status and an `https://` address and opens in a new tab. A service with no project renders a short note and the contact button instead of cards.
- **Layout.** One card is a feature layout (picture and text side by side on wide screens); two cards use two columns; three or more use three columns on wide screens (two on tablets, one on phones). Cards in a row share a height with their feet aligned on the bottom edge. Filters are written only for a catalog with at least four projects in at least two groups (`FILTER_MIN_PROJECTS`, `FILTER_MIN_GROUPS` in `catalog.js`), one button per group that has a project, so a filter never leads to an empty list. A service groups by industry, or by event type when its entry in `solutions.js` says `filterBy: 'eventType'` (004 You're Invited).
- **Spreads (`catalogLayout: 'spread'`, used by 004).** A catalog is written either as the card grid above or as one spread per project (`renderSpread` in `catalog.js`). A spread is an `<li class="catalog__item spread">` (so the shared filters still work) holding an `<article>` with two parts: the copy (number, name with the ampersand in the serif italic, description, what it contains, facts as a `<dl>`, the live link, its address and a line on how to try it) and a `<figure>` with a plate (`.spread__plate`, background `--tone` from the project's `previewTone`) carrying up to three real screens (`.spread__screen--1…3`, placed in percentages of the plate so the composition scales as one picture; two are shown on phones) and a caption saying where they come from. Spreads alternate sides at 1100 px and wider and stack below. The plate links to the live address for people with a pointer (an empty `aria-hidden` link, `tabindex="-1"`, like the card pictures); the labelled button in the copy is the link for keyboard and screen-reader users, and the screens keep their `alt` text. The copy comes first in the source, so the name is read before the pictures.
- **Spread motion (`CatalogSpreads.js`).** GSAP only, and only for people who have not asked for less motion. *Reveal*, once per spread when it is 20% in view: the plate is drawn from the top down (`clip-path`), the screens rise into it (middle one first), the name rises out of a mask and the words follow. The hidden start state is set by the script itself, only when it can play it, and only the properties it set are cleared afterwards (clearing everything would also remove the plate's colour, which lives in its style attribute). *Drift*, mouse only: the screens move against the pointer, the middle one most, through `quickTo`, and settle when it leaves; keyboard focus on the live link lifts them instead. The lavender rule along the foot of the plate is CSS (hover and `:focus-visible`). Reduced motion: no reveal, no drift, no transition on the rule.
- **Styles** live in `css/catalog.css` only (selectors `.sol-detail__foot`, `.sol-detail__catalog`, `.catalog*`, `.prow*`, `.pcard*`, `.spreads`, `.spread*`), loaded after `solutions.css`.
- **Accessibility.** The toggle is a button with `aria-expanded` and `aria-controls`; the drawer is a labelled `section`; project names are `h5` under the catalog's `h4`; each card's two links carry the project name for screen readers; the external link says it opens in a new tab; filters are `aria-pressed` buttons with a polite live region.
- **Without JavaScript** the drawer and details are plain visible content and the script-only buttons are hidden (`html:not(.js)`).

### CreativeSolutions.js

- hides the details and opens one at a time from each tile's "Details" button (`aria-expanded`, `aria-controls`); Close and Escape return focus to the tile; `#solution-<id>` links open a service, `#solution-<id>-catalog` opens its catalog too;
- opens and closes each service's catalog (`aria-expanded` in step, focus stays on the button, a minimal scroll nudge only when the start of the catalog would be off screen, no motion with reduced motion). **Escape peels one layer:** an open catalog first (focus returns to its button), then the panel. Closing or switching a panel closes its catalog; it is static markup, so nothing is re-rendered and no listener is added twice;
- runs the catalog filters (industry or event type) when the build wrote them;
- starts `CatalogSpreads.js` for the 004 spreads;
- re-reads the service data, so a demo link set on a service appears even before the HTML is regenerated;
- fits each large title word to its tile: container query units (`cqi`) set the size, and one measurement after the fonts load corrects it if a title was edited;
- adds what the CSS cannot do alone for the title motions and the scroll state: a tile is `.is-live` while it crosses the middle of the screen, so each title performs as you scroll past it, on every device. Hover, keyboard focus, an open tile and `.is-live` switch the CSS states of the three motions in use (`frame` crop marks, `build` fill sweep, `press` ink press). Two spare motions (`respond`, `gather`) stay in the code and CSS for a future tile. Reduced motion keeps the states and drops the movement.

`ConnectedLaunch.js` runs "Our signature: the connected launch", the five-stage stepper (tabs) below the mosaic. While it is in view it makes one gentle pass from the first stage to the last and then rests; it holds still while a mouse rests on it, and stops for good as soon as the visitor clicks, presses a key or moves focus into it. It never advances with reduced motion. While it advances by itself its panel is not a live region, so screen readers are not interrupted; from the moment the visitor takes over it announces their choices again. On the Invitation and RSVP stages its button opens 004 You're invited.

## Contact flow

1. **Browser.** Buttons marked `data-start-project` (with an optional `data-category`) switch to the project tab and preselect the matching project type: "Start a project like this" (in each Details panel) and the "Start a project" button that closes each catalog both use this one mechanism, so there is a single contact flow. The project brief is four steps in one `<form>`: project type, description, timing and budget (optional), contact details with a review of the earlier answers. Continue validates only the current step; Back and the review's Edit buttons keep every answer, because hidden steps stay in the form. Enter moves on, and in the last step it sends. Without JavaScript the four steps show as one long form. The form validates every field, with errors announced. A honeypot field and a 2.5 s time trap catch bots, and `elapsedMs` is sent along. Optional Turnstile loads only once the visitor interacts with the form. The send has a timeout through AbortController. Success is shown only when the provider confirms; on failure, the visitor's answers stay in place.
2. **Google Apps Script** (the configured provider). A simple CORS request: POST with a `text/plain` body holding JSON, so the browser sends no preflight (Apps Script cannot answer one). Google redirects to `script.googleusercontent.com`, whose JSON response carries `Access-Control-Allow-Origin: *`, so the page reads `success`/`error` and reports the real result. A sign-in page (deployment not public), a timeout or `success:false` is an error; answers are kept. "Just say hello" is sent as Project Type "General Inquiry". Reference script: `server/google-apps-script/Code.gs`.
3. **Not configured.** The form says so and offers a copy of the message. It never pretends to send.
4. **Cloudflare Worker** (`server/contact-worker.js`, optional, not used with Apps Script). Checks the CORS allow-list and the body size, validates again, drops spam silently, verifies Turnstile, applies a soft KV rate limit, and sends through Resend with reply-to set to the visitor. It stores nothing.

## Accessibility

- Native `<dialog>` for the intro and menu, which gives focus containment and Escape. Focus returns to the opener.
- A skip link and landmarks; one `h1` per page; headings in order.
- Visible focus everywhere, a lavender ring on dark sections.
- Labels and error messages tied to fields with `aria-describedby` and `aria-invalid`.
- Live regions for form results and for the visitor's own choices in the launch story and the hero panel. The automatic passes (hero, launch story) are silent.
- Reduced motion is honoured everywhere.
- Layout breakpoints are written in `em`, not `px`, so a reader who has raised the browser's default text size gets the compact header and single-column layouts sooner instead of clipped navigation. At the normal 16 px size they land on the same widths as before (900 px = 56.25em).
- Small links (breadcrumbs, the contents list of the notices, the live-site address on a case study) have a taller tap area than their text, made with padding cancelled by an equal negative margin, so nothing moves; on touch screens the contents entries become full rows.
- Horizontal galleries are focusable regions with labels.
- Links, buttons, fields, labels, summaries and tabs carry `touch-action: manipulation` (`css/base.css`), so a quick second tap on a toggle, a tab or a chip is not read as a double-tap zoom on iOS. Scrolling and pinch zoom are untouched. The effect itself has not been checked on a real iPhone.
- Contrast is checked against the tokens.

## Testing done

Automated in headless Chromium (the Playwright library) with software WebGL (SwiftShader), serving the folder over HTTP, plus a run with the pages opened straight from disk. The scripts are not part of the delivery. The latest round (invite_final_10) ran **660 checks in 23 scripts, all passing**, on the folder that became the ZIP (invite_final_6 ran 513 in 19); `docs/REFINEMENT.md` lists them against the brief's test list and says what could not be run. Covered:

- **Layout.** Every page at 1440 and 390 px; navigation and overflow at every width from 320 to 1920 px; the hero's layout shift (about 0 from 320 to 2200 px); the browser's default text size at 150 % and 200 %.
- **Intro.** Full (2.8 s), short (1.2 s) and classic (5.6 s); Skip, Escape (also as the very first action), Replay, reload, section links, Back from another page; reduced motion (still frame); no WebGL; no GSAP; scripts blocked (failsafe); a 6× slower CPU.
- **Creative Solutions.** Four services in order with their numbers, names, categories and structured data; four title motions; Details panels (click, keyboard, Escape, `#solution-…` links including the retired ids, rapid presses); every catalog, including the empty one; filters.
- **Hero.** The three-stage figure (hover, tap, keyboard, Escape, one pass, reduced motion) and the strip of service links.
- **Selected Work.** The three blocks (Casa Gelso, JETOUR and the generated wedding-invitations block with its live links); Casa Gelso's screen tabs and its single pass; the JETOUR film (muted, plays on screen, Pause and Play, no restart after a Pause, never by itself with reduced motion, restart after an aborted load); the connected launch story (one pass, silent while it runs by itself, hover hold, stops on click, key or focus).
- **Contact.** The four-step brief and "Just say hello" against mocked responses (success, rejection, timeout, network failure, not connected); the request is one `text/plain` POST with the field names the Apps Script reads; taps on Back and Continue with touch emulation.
- **Keyboard and focus.** A full Tab walk on every page, a visible ring of at least 4.9:1 on every stop, the menu dialog, skip link, tab groups.
- **Accessibility checks.** Names, labels, alt text, duplicate ids, heading order, contrast, WCAG 2.2 target size, reduced motion, and the pages without JavaScript.
- **Crawl.** Every internal link, script, stylesheet, image, srcset candidate, poster, video source and icon answers 200; every `#` link resolves; the module imports and asset paths exist.
- **Opened from disk.** The offline copy: intro, fonts, Creative Solutions, navigation to the case studies and back, and the contact form.
- **Earlier rounds, not re-run in the latest one because the code is unchanged.** The form against mocked Formspree, Web3Forms and custom endpoints (including Turnstile); the Worker in Node against mocked Resend and Turnstile (the body-size guard added since was checked against mocked requests).
- **Performance.** Indicative only, in a lab and not Lighthouse. invite_final_6 measured about 620 KB in 46 requests (uncompressed) once the homepage had loaded, about 980 to 990 KB after scrolling all of it (the JETOUR film is about 240 KB of that, fetched only when it comes into view). invite_final_10, behind a gzip server like GitHub Pages and on a 4× slower CPU with Slow 4G: about 312 KB in 46 requests at load on a 390 px phone, largest content at 1.4 s, layout shift 0.0053 or less. The figures and their limits are in `docs/REFINEMENT.md`.

Not tested: real phones, Safari and Firefox, screen readers, how the sound sounds, the MP4 version of the film, a deployed Worker, a real submission to the Google Sheet, real email delivery.
